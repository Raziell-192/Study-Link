# StudyLink

## Plataforma Móvil de Aprendizaje Colaborativo Universitario

---

# 1. Descripción General
StudyLink es una aplicación móvil orientada a estudiantes universitarios que busca facilitar el aprendizaje colaborativo mediante tutorías, grupos de estudio, intercambio de recursos académicos y herramientas de organización personal.

La plataforma permitirá conectar estudiantes con intereses académicos similares, fomentar la colaboración entre pares y proporcionar recursos que ayuden a mejorar el desempeño académico.

---

# 2. Problemática
Los estudiantes universitarios suelen enfrentar dificultades para:
* Encontrar compañeros de estudio.
* Organizar sesiones académicas.
* Acceder a materiales de apoyo confiables.
* Encontrar tutores adecuados para temas específicos.
* Dar seguimiento a sus objetivos de aprendizaje.
* Mantener hábitos de estudio constantes.

Actualmente estas actividades suelen realizarse mediante múltiples aplicaciones separadas, generando desorganización y pérdida de información.

---

# 3. Objetivo General
Desarrollar una aplicación móvil que integre herramientas de tutoría, colaboración académica, gestión de recursos educativos y seguimiento del progreso estudiantil.

---

# 4. Objetivos Específicos
* Facilitar la conexión entre estudiantes con intereses similares.
* Permitir tutorías individuales y grupales.
* Compartir materiales académicos.
* Organizar sesiones de estudio.
* Gestionar objetivos de aprendizaje.
* Medir el progreso académico.
* Incentivar la participación mediante gamificación.

# 22. Requisitos No Funcionales
* **RNF-01 (UX/UI):** La interfaz debe ser intuitiva, fluida y moderna, construida bajo las directrices de **Material Design 3**.
* **RNF-02 (Seguridad):** La información sensible debe almacenarse y transmitirse de forma cifrada (HTTPS/SSL y hash para contraseñas).
* **RNF-03 (Rendimiento):** El tiempo de respuesta del servidor ante solicitudes REST API debe ser inferior a 3 segundos.
* **RNF-04 (Compatibilidad):** Multiplataforma nativa para Android (SDK 21+) e iOS (iOS 13+) desde una sola base de código.
* **RNF-05 (Disponibilidad):** Garantizar un uptime continuo mediante arquitectura en la nube.
* **RNF-06 (Diseño Responsivo):** Adaptabilidad total de componentes gráficos a pantallas de smartphones y tablets.
* **RNF-07 (Persistencia Offline):** La aplicación debe permitir el acceso y edición de datos locales (Flashcards individuales, objetivos y calendario) sin conexión a internet.

# 23. Tecnologías y Arquitectura

## 23.1 Stack Tecnológico
* **Frontend:** Flutter & Dart (Framework multiplataforma nativo).
* **Backend:** Node.js con Express.js (API REST estructurada en JSON).
* **Base de Datos Remota:** PostgreSQL (Persistencia relacional escalable).
* **Base de Datos Local (Offline):** **Isar Database** (Base de datos NoSQL embebida de alto rendimiento para persistencia local en Flutter).
* **Almacenamiento en la Nube:** Firebase Storage (Para PDFs e imágenes de apuntes).
* **Notificaciones:** Firebase Cloud Messaging.
* **Control de Versiones:** Git y GitHub.

## 23.2 Patrón de Arquitectura de Software
Se implementa el patrón arquitectónico **MVVM (Model-View-ViewModel)** combinado con los principios de **Clean Architecture**, dividiendo el software en tres capas desacopladas para separar de manera estricta la interfaz de usuario de la lógica del negocio:

1. **Capa de Presentación (Views):** Widgets reactivos de Flutter que renderizan la UI siguiendo las pautas de Material Design 3.
2. **Capa de Lógica (ViewModels / BLoC / Cubit):** Controladores encargados de gestionar el estado de la aplicación, interceptar eventos del usuario y solicitar la información a los repositorios.
3. **Capa de Datos (Repositories & DataSources):** Módulo encargado de gestionar las fuentes de datos. Utiliza una estrategia de repositorio condicional: si el dispositivo tiene acceso a internet, consume los servicios de la API REST de Node.js; si detecta pérdida de conectividad, conmuta transparentemente a Isar DB para extraer la información local guardada.
